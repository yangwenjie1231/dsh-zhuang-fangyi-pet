# 跨平台桌宠方案调研（结论：不另开 Electron，但**也不止窗口内**）

> **2026-10-04 修订**：本文件最初的结论是「只能做窗口内悬浮层」，因为候选方案只列了
> 五种。**那个选择集漏了最优解** —— 由插件宿主用官方 `ctx.subprocess` 启动一个
> 我们自己编译的 **.NET Framework 4.8 小 exe**。它同时做到「真的浮在桌面上」
> 与「零安装、内存低、不碰 DSH 的 IPC 白名单」。详见文末「修订后的结论」。

## 问题

桌面版 DSH 的桌宠若走「原生透明置顶窗口」，需要额外跑一个 Electron/Chromium 实例，
内存占用大（+80~150MB），且每个平台各需一份二进制。是否存在更省、可跨平台的做法？

## 桌面壳的硬约束（已从 `resources/app.asar` 源码核实）

| 事实 | 依据 |
|---|---|
| 桌面版是**双进程**：Electron 主进程 `spawn` 独立 Node 宿主进程 | `lib/main.js`：`spawn(node, [... 'dsh-desktop-host/lib/index.js'], { stdio:[ignore,pipe,pipe,ipc] })` |
| **Host 半身跑在纯 Node 进程**，无 Electron API | 同上；`dsh-desktop-host` 只 `runProfile` |
| 主进程 IPC 是**封闭白名单** | 只有 `directoryPick` / `browserAcquire|Release` / `platform.*` / `windowsAppearance` / `windowsMenu` / `nativeThemeSet` 等，**无开窗通道** |
| 宿主→主进程的 IPC 只接受固定消息类型 | `child.on("message")` 仅处理 `ready` / `platform-session` / `shutdown-complete` / `fatal` / 受控 `controlRequests` |
| 渲染层 `window.open` 被一律拒绝 | 主窗口、登录窗、强制更新窗全部 `setWindowOpenHandler(() => ({ action: "deny" }))`（asar 内实测 7 处） |
| 宿主进程**自带 koffi（原生 FFI）** | `dsh-desktop-host/node_modules/koffi/`（含 `win32_x64/koffi.node`） |
| **宿主有官方 `ctx.subprocess` 受管子进程接缝** | 本机实测：两个 `DeepSeek Harness.exe` 在跑 `dsh-subprocess-local\lib\runner.js`；`dsh-pwsh-sandbox` 声明 `inject=["subprocess",…]` 且工作正常 |

→ **插件无法让宿主或主进程为自己开一个原生窗口。**
→ **但插件可以让宿主启动自己的进程** —— 这是关键区别。

## 现有原生桌宠怎么做到的

`dsh-pet-live2d` 的做法是**自带独立二进制**：

- `dsh-pet-live2d`（主包）+ `dsh-pet-live2d-desktop-win32-x64`（9.2MB `bin/dsh-pet-live2d-desktop.exe`）
- 即：又一个 Electron 实例，且按平台分包发布

## 候选方案对比

| 方案 | 额外内存 | 跨平台 | 工程成本 | 能"站在桌面上" |
|---|---|---|---|---|
| ① `shell.overlay` 页面内悬浮层 | **0** | **全平台同一套代码** | 低 | 否（在窗口内） |
| ② 自带 Electron exe | +80~150MB | 差（每平台一份） | 高 | 是 |
| ③ Tauri / 原生小程序（Rust/C#/Python） | +10~30MB | 中（仍需各平台构建） | 高 | 是 |
| ④ 借桌面壳主进程开窗 | — | — | — | **不可行** |
| ⑤ koffi FFI 直接建窗口 | 低 | **差**（三套 API） | 极高 | 是 |
| **⑥ `ctx.subprocess` + 自编译 net48 WPF 小 exe** | **~50MB** | Windows 优先（其它平台回落 ①） | 中 | **是** |

## 修订后的结论

**桌宠采用「⑥ 原生窗为主 + ① 窗口内 overlay 兜底」的混合形态。**

方案 ⑥ 的三条硬指标都已在本机实测钉死（不是推测）：

1. **`.NET Framework 4.8` 零安装** —— Win10 1903+ / Win11 系统自带
   （本机 `Release=533509`）。交付物只是一个 **~12 KB 的空壳 exe**
   （实际含代码与素材引用约 30~150 KB）。
2. **离线可编译** —— 用 .NET SDK 自带的 Roslyn `csc.dll` 直接编 net48，
   完全不需要联网或 NuGet 还原。产物只需 exe 本体，**不需要 `.exe.config`**。
3. **alpha 点击穿透真的成立** —— `HwndSourceHook` 拦 `WM_NCHITTEST`，
   透明像素返回 `HTTRANSPARENT`（实测 -1），不透明像素放行（实测 1）。

**为什么这比方案 ② 好得多**：Electron 要打包一整个 Chromium（+80~150MB、
按平台分包），而 net48 的 WPF 直接用系统自带的运行时，**一个 12KB 的 exe 就够了**。

**为什么不选方案 ③（Tauri）**：Tauri 仍需各平台构建工具链（Rust + 各平台 SDK），
而 WPF 在这台机器上**已经能离线编译**，且不需要引入任何新依赖。
若将来真要跨平台原生窗，再考虑 ③。

**方案 ①（窗口内 overlay）保留为兜底**，在下列情况自动接管，功能完整只是不浮在桌面上：

- 非 Windows 平台；
- 宿主未提供 `ctx.subprocess`（Web profile 或旧版本）；
- exe 未构建 / 被杀软删除 / 秒退（宿主会在快照里给出 `nativeError` 与原因）；
- 用户把 `mode` 设为 `overlay`。

**这不碰 DSH 的 IPC 白名单**：那条白名单限制的是「让 DSH 替我开窗」，
不限制「我自己 spawn 一个进程」；而 `ctx.subprocess` 是官方受管接缝
（服务 dispose 时会终止所有受管进程，所以关掉 DSH **不会留下孤儿桌宠**）。

具体实现见 [`桌宠开发文档.md`](桌宠开发文档.md) 与
`dsh-zhuang-fangyi-pet/docs/接口契约.md`。
