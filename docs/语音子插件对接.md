# 语音合成子插件 · 对接说明

> 面向 [`dsh-zhuang-fangyi-voice`](https://github.com/yangwenjie1231/dsh-zhuang-fangyi-voice)。
> 桌宠这边**已经准备好了**：装好语音插件即自动接管，无需改代码。

---

## 一、两种接法（桌宠自动选）

桌宠启动时探测宿主上有没有 `zfhVoice` 服务，据此走不同的路：

| 情况 | 谁管进程 | 桌宠做什么 |
|---|---|---|
| **装了语音 DSH 插件**（推荐） | 语音插件 | 只调 `zfhVoice.synthesize(text)`，并把设置推给它 |
| **只跑了独立服务**（`python -m zfh_voice serve`） | 你自己 / 桌宠兜底 | 走 HTTP `POST /tts`；没配启动命令就只连不管 |
| **都没有** | — | 退回固定台词，**聊天完全不受影响** |

设置页「合成服务」那一行会写明当前是哪种：`由语音插件托管` /
`运行中（桌宠启动的）` / `运行中（你自己启动的）` / `未运行`。

**为什么要有两条路**：语音插件是 DSH 插件（推荐，开关统一、进程托管完整）；
但它也可能被当成独立服务跑（CI、别的宿主、只想手工起）。两条都覆盖，
而且各自都有测试。

## 二、桌宠调用什么

装了语音插件时（服务面）：

```js
const voice = ctx.get('zfhVoice')
const r = await voice.synthesize('做完了，你看看。')   // → {bytes, durationMs, backend} | null
voice.status()                                        // 只读状态
voice.start() / voice.stop()                          // 显式控制
voice.configure({resident, idleStopSec, …})           // 桌宠把设置页的开关推给它
```

没装插件时（HTTP，即语音插件 Python 侧的契约）：

| 用途 | 请求 | 期望响应 |
|---|---|---|
| 健康检查 | `GET /health` | `{"ok":true,"backend":"torch"\|"onnx","version":"…"}` |
| 合成一句 | `POST /tts`，body `{"text":"……"}` | **`audio/wav` 二进制**（RIFF 头） |

### 桌宠对响应的三条硬要求

1. **必须是 RIFF/WAV** —— 否则整条结果被丢弃；
2. **单条不超过 8 MB** —— 超过即丢弃（防"服务返回一整个音频文件"把磁盘写爆）；
3. `Content-Length` 正确（或正常分块）。

不满足时桌宠**静默退回固定台词**，聊天不受影响，日志里记一行。

## 三、桌宠侧的开关（设置页 → 语音）

| 设置 | 默认 | 说明 |
|---|---|---|
| `speakReplies` | **关** | 把 AI 的回答念出来。关着时**完全不调用**合成 |
| `voice` | **关** | 语音总开关；它关着时即使 `speakReplies` 开着也不合成 |
| `ttsResident` | **关** | **常驻**：一直占显存但合成立刻开始；关：空闲后释放显存 |
| `ttsIdleStopSec` | `300` | 非常驻时空闲多少秒释放（0 = 不停） |
| `speechMaxChars` | `60` | 单句朗读上限（清洗后截断到句子边界） |
| `ttsUrl` | `http://127.0.0.1:8765` | 走 HTTP 那条路时的地址 |
| `ttsPython` / `ttsRepoDir` / `ttsBackend` | 空 = 自动 | 走 HTTP 且要桌宠托管进程时才用 |

设置页有三个按钮：**试一句**（真合成并播放，验证链路）、
**启动服务**、**停止并释放**（立刻起/释放，不等空闲超时）。

> ⚠️ **桌宠里没有任何绝对路径**。语音插件的位置按这个顺序找：
> 设置 → 环境变量 `DSH_ZFH_VOICE_DIR` / `ZFH_VOICE_DIR` → **与桌宠同级的
> `node_modules`**（DSH 插件管理器装的话就在那儿）→ 并排签出的目录。
> python 同理：设置 → `ZFH_VOICE_PYTHON` → 仓库里的 `.venv` → PATH。
> 所以同一份配置在任何人的机器上都能用。

## 四、端到端链路

```
AI 回复（markdown）
   ↓ 清洗：去代码块/链接/markdown 标记/emoji，截到句子边界
可朗读文本
   ↓ zfhVoice.synthesize()（或 HTTP POST /tts），异步、fire-and-forget
WAV 字节
   ↓ 落盘 $DSH_HOME/zhuang-fangyi-pet/speech/<16位缓存键>.wav
快照 speak: {seq, name, durationMs}
   ↓ exe 发现 seq 变化 → GET /pet/speech/<name>
播放
```

设计要点：

- **异步**：气泡先显示文字，语音好了再播。onnx 后端一句 6 秒的话要 37 秒，
  同步等它等于聊天卡死；
- **缓存键 = 文本 + 服务身份**（后端名）：换音色/后端后同一句话会自动重新合成
  （只按文本做键会让换音色后仍播旧音，而且毫无报错）；
- **代际丢弃**：连发几条时，先发的那句合成完若已过期就丢弃（不盖住更新的那句）；
- **exe 按 `name` 去重**（不是 `seq`）：宿主重启后 seq 归零，按 name 去重
  不会把同一句重复念一遍。

## 五、日志里怎么确认它在工作

`$DSH_HOME/zhuang-fangyi-pet/boot.log`：

| 行 | 含义 |
|---|---|
| `动态语音就绪（新合成，2400ms）：做完了…` | 合成成功并已交付 exe |
| `动态语音就绪（缓存，2400ms）` | 命中缓存，没重复合成 |
| `动态语音合成不可用 → 退回固定台词` | 服务没起 / 超时 / 返回非 WAV |
| `动态语音已过期（有更新的回复）→ 丢弃` | 代际丢弃（正常） |

语音插件侧（宿主日志）：`庄方宜语音：已挂载 zfhVoice 服务`、
`庄方宜语音：服务就绪（38s，backend=torch）`、`已停止服务（释放显存）`。

exe 侧（`%LOCALAPPDATA%\DSH-ZhuangFangyi-Pet\pet.log`）：
`动态语音播放: <name>（2400ms）`。

## 六、后端选择（直接影响体验）

| | RTF | 6 秒音频 | 占显存 |
|---|---|---|---|
| **torch** | ≈ 0.45 | 约 3 秒 | 要（几 GB） |
| **onnx** | ≈ 6.1 | **约 37 秒** | 不要 |

> ⚠️ onnx 后端逐句交互基本不可用（37 秒后气泡早消失了）。
> 有显卡就用 `torch`。若只能用 onnx，把「每次朗读字数上限」调到 20~30 字。

安装步骤与排错见语音插件仓库的 `docs/安装提示词.md`
（那份文档可以**整段复制给 AI 助手**，让它替你配好环境）。
