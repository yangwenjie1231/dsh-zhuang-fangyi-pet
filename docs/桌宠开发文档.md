## 二、为什么能「零桥接」拿到状态

这是整份文档最重要的一节。**桌宠不需要任何人给它转发状态** —— 它自己能读到。

### 2.0 ⭐ 关键更正：**根 Context 能收到全部 scoped 事件**（实测）

原文 §2.2 担心 `retain()` 的引用计数泄漏（忘了 `release()` 会阻止会话卸载）。
**这个担心在本方案里不存在**，因为根本不需要 `retain()`。

`@deepseek-ai/dsh-scope` 的 `scopeTarget()` 过滤器（源码实测）：

```js
const carrier = { [Context.filter](ctx) {
  if (baseFilter !== void 0 && !baseFilter.call(base, ctx)) return false
  const tag = scopeOf(ctx)
  if (tag === void 0) return true          // ← 无 tag 的监听者（根 Context）一律放行
  for (let cursor = key; cursor !== void 0; cursor = scopeParents.get(cursor))
    if (cursor === tag) return true
  return false
} }
```

所以：**在根 Context 上 `ctx.on('agent/status', …)` 就能收到所有会话的事件。**
作用域语义是「事件沿父链**向上**流动，绝不向下」—— agent 作用域的监听者只收到
那一个 agent，根监听者收到全部。我们要的正是后者。

### 2.1 两条路：Client 侧事件 vs DOM 推导

| 方式 | 拿到什么 | 优点 | 缺点 |
|---|---|---|---|
| **① Client 侧订阅官方事件/服务** | 精确的运行状态 | 权威、即时、不碰 DOM | 需要正确的 `inject` 声明 |
| **② 读 DOM 语义锚点** | 界面**实际呈现**的状态 | 不需要任何服务 | 需要解析 DOM，状态是推导的 |
| **③ Host 侧根监听（本方案采用）** | 精确的运行状态 | 权威、即时、**不需要 retain、不碰 DOM** | 需要宿主半边 |

**原生窗用 ③**（它在宿主进程里，拿不到 DOM）；**窗口内兜底用 ③ 的快照**（同一个状态机）。
所以 ①②③ 三条路里，**只有 ③ 是必需的**，①②在本方案里都不需要。

### 2.2 Client 侧可用的权威来源（已核实）

`dsh-client-ui-slots` 之外，Client 侧还有这些服务：

```js
// 会话状态的权威来源 —— SessionSnapshot 里有 running
ctx.sessions.retain(target, { source })      // 拿到 SessionReference
  → reference.binding.session.getSnapshot()  // SessionSnapshot
```

`SessionSnapshot` 的关键字段（从 `SessionReference` 类型定义实测）：

```ts
interface SessionSnapshot {
  readonly sessionId: SessionId
  readonly running: boolean          // ← 桌宠最需要的
  readonly pendingSubmissions: readonly PendingSubmission[]
  readonly openState: 'cold' | 'loading' | 'open' | 'error'
  readonly openError: RemoteFailure | null
  readonly promptError: PromptError | null   // { op: 'send' | 'stop', error }
  readonly blank: boolean
  readonly lastAgentError: string | null     // ← 出错状态的权威来源
  readonly awaitingFirstTurn: boolean
  readonly removed: boolean
  readonly hasMore: boolean
  readonly loadingOlder: boolean
}
```

订阅方式（`ObservableSnapshot` 契约）：

```js
const session = reference.binding.session
const unsub = session.subscribe(() => {
  const snap = session.getSnapshot()
  // snap.running / snap.lastAgentError …
})
```

> **`retain()` 是引用计数**，用完必须 `release()`（或用 `using()` 自动释放）。
> **但本方案不需要它** —— 见 §2.0：宿主侧根监听即可拿到全部状态。
> 只有在做**纯 Client 侧**插件（无宿主半边）时才需要 `retain()`，那时务必成对释放。

### 2.3 Host 侧事件（**本方案的实际数据源**）

Host 进程有完整的事件流（`cordis_inspect_query(host, Event, listEvents)` 查到 78 个），
实测签名如下（全部为 `platform=host` 的真实返回）：

| 事件 | mode | 签名 | 用途 |
|---|---|---|---|
| `agent/status` | emit | `(this: Scoped<Agent>, payload: { agent, status: 'idle' \| 'running' })` | **最核心**：idle ⇄ running |
| `agent/error` | emit | `(this: Scoped<Agent>, payload: { agent, turn, step, error })` | 出错时切表情 |
| `agent/turn-stopping` | **serial** | `(this: Scoped<Agent>, payload: { agent, turn, signal })` | 回合收尾（**注意是 serial，不是 emit**） |
| `agent/inbox/inserted` | emit | `(this: Scoped<Agent>, payload: { agent, message })` | 有新消息 |
| `tools/result` | emit | `(this: Scoped<ToolRuntime>, exec, result)` | 工具调用结果（按 `exec.agent` 路由） |
| `api-session/status` | emit | `(sessionId, running: boolean)` | 任意会话的运行状态（**非 scoped**） |
| `api-session/error` | emit | `(sessionId, message: string)` | 回合外的失败（**非 scoped**） |
| `session/event` | emit | `(this: Scoped<Session>, session: Session, event: SessionEvent)` | **durable 事件流，含 `turn/end`** |

**注意作用域**：前五个是 `Scoped<T>` 派发的（`@deepseek-ai/dsh-scope`），
但**根监听者一律收到**（见 §2.0）。`api-session/*` 完全不带作用域。

#### ⭐ 「完成」的信号：原文说没有，实际有 —— 在 `session/event` 里

原文 §4 只能用 DOM 锚点 `turn-tail` 猜「完成」。**宿主侧有权威信号**：

```ts
'turn/end': { turn: number; reason: TurnEndReason }

export interface TurnEndReasonMap {
  completed:    { kind: 'completed' }                          // ← "完成"
  aborted:      { kind: 'aborted'; reason: TurnEndCancelCause }
  blocked:      { kind: 'blocked' }
  error:        { kind: 'error'; error: LlmFailure }           // ← "出错"
  'max-tokens': { kind: 'max-tokens' }                         // ← 输出被截断
  interrupted:  { kind: 'interrupted' }
}
```

**实测确认 `agent/status` 只带 `'idle' | 'running'`，没有 `done`** ——
所以「完成」必须从 `turn/end` 的 `reason.kind === 'completed'` 取。
这是本方案比原文档精确的地方。

`SessionEventMap` 里其它可用事件（实测自 `dsh-session/lib/types/types.d.ts`）：
`turn/start`、`step/start`、`step/end`、`tool/call`（带 `callId`/`name`）、
`tool/result`（带 `error?`）、`user/message`、`approval/asked`。

> **注意**：`session/event` 是 **post-commit、fire-and-forget** 的
> （监听者失败被记录并容纳），状态有毫秒级延迟，对桌宠表现无影响。

## 三、渲染层：`shell.overlay`

### 3.1 插槽契约（实测自 `Slots.listSubTree`）

```
name:        shell.overlay
kind:        list
scope:       root
replaceRisk: none          ← 加性席位，不替换任何已装 UI
registration: { id: string (required), order?: number, label?: string | (() => string) }
```

用途原文：

> Frame-wide floating layer, above every column and outside their scroll containers.
> Deliberately generic and unowned by any feature: a badge, a toast stack or a
> status pill all belong here... **The layer itself is click-through — entries opt
> back into pointer events — so an occupant never blocks the app underneath.**
> This is the additive seat for a frame-wide surface of your own: a fresh `id` is
> added beside the shipped entries instead of replacing them.

**三个关键含义**：

1. **层级在整个框架之上、各栏滚动容器之外** → 宠物拖到哪都不会被裁切；
2. **默认穿透**（`pointer-events: none`）→ 宠物本体要显式开 `pointer-events: auto`，
   否则点不到；
3. **新 `id` 是加性的** → 不会与官方或其它插件冲突（已核实：该槽现有 10 个官方条目）。

### 3.2 渲染容器不是普通 div —— 三个已实测的坑

```css
.BynINW_overlayLayer{ z-index:20; pointer-events:none; position:absolute; inset:0 }
.BynINW_overlayLayer>*{ pointer-events:auto }
```

**坑 1：绝对定位会偏。** `overlayLayer` 是 `AppFrame`（`display:grid`）的**第 4 个
子元素**，而三个列 + overlay **都没写 `grid-area`**，全靠自动放置：

```css
.BynINW_frame{ display:grid; grid-template-rows:100% }
[data-windows-titlebar] .BynINW_frame{
  padding-top:40px; grid-template-rows:minmax(0,1fr)   /* 只有 1 行 */
}
```

三列填满第 1 行后，**overlay 溢出到隐式第 2 行** —— 它的包含块下移将近一屏
（实测：`position:absolute; top:40px` 的元素落在 y≈572）。

→ **宠物必须用 `position:fixed`**（相对视口），并自己让开 Windows 标题栏：

```css
.zf-pet{ position:fixed; ... }
html[data-windows-titlebar] .zf-pet{ /* 若需贴顶：top: var(--dsh-windows-titlebar-height) */ }
```

**坑 2：子元素自动 `pointer-events:auto`。** 外壳对 overlay 的**直接子元素**开了
`pointer-events:auto`。若宠物容器铺满全屏（`inset:0`）就会挡住整个界面。
→ **容器要小**（只包住宠物本身），或显式 `pointer-events:none` 再给本体开。

**坑 3：`z-index:20` 是 overlay 层的。** 宠物自己的层级别超过必要的层级；
官方菜单栏（`dsh-windows-menu`）是 `z-index:1100`，别去盖它。

### 3.3 最小可用骨架


## 四、状态机设计

桌宠的表情应该由**一个聚合状态**驱动，而不是每个来源各改各的。建议：

```js
const PET_STATES = [
  'idle',       // 空闲（呼吸/眨眼）
  'thinking',   // 模型思考中
  'working',    // 工具调用中
  'happy',      // 回合完成
  'error',      // 出错
  'sleeping'    // 长时间无操作
]
```

### 4.1 推导优先级（照抄主题插件已验证的顺序）

```
tool > running > error > done > ready > idle
```

理由（来自外壳行为）：**历史错误不该覆盖当前回合**。所以先按「最后一个 user
消息」切出当前回合，只在当前回合里判断。

### 4.2 两个来源的合并

```js
function deriveState ({ snapshot, dom }) {
  if (snapshot?.lastAgentError != null) return 'error'
  if (snapshot?.running === true) {
    return dom?.hasRunningTool === true ? 'working' : 'thinking'
  }
  if (dom?.turnDone === true) return 'happy'
  return snapshot == null ? 'idle' : 'idle'
}
```

`dom` 从语义锚点读（与主题插件同源，已实测存在）：

| 锚点 | 含义 |
|---|---|
| `[data-chat-flow-kind="tool-call"] [data-state="running"]` | 工具调用进行中 |
| `[data-streaming="true"]` | 正在流式输出 |
| `button[aria-label="停止生成"]` / `"Stop generating"` | 可中断 = 运行中 |
| `[data-chat-flow-kind="turn-tail"]` | 回合收尾 = 完成 |
| `[data-chat-flow-kind="turn-error"]` / `turn-max-tokens` | 出错 |

> 这组锚点是从桌面壳 456 个 `data-*` 里筛出来的，**跨版本比类名稳**。

### ⭐ 修订：怎么判断一张 GIF「能不能直接用」

**判据：逐帧统计「`alpha == 0` 的像素占比」。**

理由直接来自需求：桌宠的硬要求是「**任何一帧都不能铺满不透明像素**」，
否则播放到那一帧会出现一个**矩形色块**。这是定义本身，不需要阈值猜测。

实测结果（`minT%` = 全部帧里最小的透明占比）：

```
干净（10 张，可用）：01(16.5) 02(6.5) 03(17.8) 04(11.9) 06(8.6) 07(9.9)
                    24(37.5) 26(54.8) 28(44.1) 29(40.7)
有实心帧（2 张，排除）：05_星空公式(33/33 帧 0%)、27_生气指人(10/18 帧 0%)
```

**⚠️ 两个被验证为不可靠的判据（都踩过）**：

| 判据 | 为什么错 | 误判实例 |
|---|---|---|
| **内容 bbox 是否铺满** | 主体**画到画面边缘**（鼓脸、肩甲、盘子）就会被判成"有板" | 误判 01/02/24/27/28/29 |
| **洋红底透过率** | 主体**占满画面宽度**就会压低透过率 | 误判 02/26/29 为脏、06/07 为脏 |

只有**逐帧透明像素占比**能直接回答「这一帧会不会显示成一个块」。
`tools/prepare-pet.py` 已把该判据固化（阈值 `<0.5%` 即判 `needsCutout`），
`--check` 会逐张打印 `minT%`，用户以后丢新图进来自动判定。

### 素材处理（实际做法）

**产出横向精灵条带，而不是动图 WebP —— 一份产物喂两个消费者**：

- 原生 exe 用 `CroppedBitmap` 取帧（v4.8 实测可用）；
- 窗口内 overlay 用 CSS `animation: steps(N)` 播同一张图；
- 两者共用同一份 `pet.json` 时序，**行为不可能分叉**。

**必须遵守的四条**：

1. **保留 alpha**：RGBA PNG，**绝不 `flatten()`、绝不贴白底** ——
   否则透明区残留 RGB 会变成彩色噪点（主题插件踩过，缩略图上一片噪点）；
2. **帧高统一 256px**（本机 150% DPI，小了会糊）；
3. **⭐ 单帧宽度必须写进清单**：单帧**不是方的**（实测 239~288px 宽，
   取决于素材 bbox 纵横比 0.85~1.13）。契约 §4 的 `frameWidth` 是**必需字段** ——
   两侧都不能拿 `frameHeight` 当宽度，否则图被横向压扁、切状态时宽度跳变；
4. **动画帧必须用「并集 bbox」统一裁切**，不能逐帧各裁各的 ——
   否则每帧偏移不同，人物会在帧间**抖动**（实测踩过）。

**待抠图的部分**：17 张纯白底 PNG + 上述 2 张 GIF，**由用户手动抠**。
管线只做「标记 + 暂存 + 报告」，不做任何键控。抠好的图放进
`art/pet/src/cutout/`（命名 `<状态名>.png` 或 `<状态名>-N.png`），重跑脚本自动纳入。

> 输出目录 `art/pet/`，由宿主路由白名单服务（**照抄**主题插件的
> `artWhitelist()` 思路 + `path.resolve` 二次校验，别自己拼路径 —— 那是目录遍历漏洞）。

## 六、交互

### 6.1 拖动

用 Pointer Events（不是 mouse）：

```js
onPointerDown: e => {
  e.currentTarget.setPointerCapture(e.pointerId)   // 关键：捕获后才不会丢事件
  dragRef.current = { x: e.clientX, y: e.clientY, ox: pos.x, oy: pos.y }
}
onPointerMove: e => { /* 算新位置 */ }
onPointerUp: e => e.currentTarget.releasePointerCapture(e.pointerId)
```

位置持久化到 `localStorage`（**别写宿主**：这是纯前端偏好，无需跨设备同步）。

### 6.2 点击与穿透

- 宠物**本体**：`pointer-events: auto`（能点、能拖）
- 宠物**周围**：不要铺满全屏容器，否则挡住界面
- 建议加「点击穿透」开关：开启后容器 `pointer-events: none`，宠物只作为装饰

### 6.3 边界约束

拖出视口后要能找回来：clamp 到 `[0, innerWidth - w]` / `[0, innerHeight - h]`，
并在 `resize` 时重新 clamp。

## 七、与主题插件的联动（可选，松耦合）

主题插件把配色写在 CSS 变量上（`--dsw-alias-*`），桌宠**直接读变量**即可，
不需要任何 API：

```css
.zf-pet{
  filter: drop-shadow(0 6px 14px color-mix(in srgb, var(--dsw-alias-brand-primary) 30%, transparent));
}
.zf-pet__badge{ color: var(--dsw-alias-brand-primary) }
```

这样**主题换配色，桌宠自动跟随**，且两者零耦合 —— 桌宠在没装主题插件时也能正常工作
（`var()` 有外壳默认值兜底）。

> **不要**让桌宠读主题插件的设置文件。那是实现细节，会锁死两个插件的版本关系。

### 测试做法（**实测有效**）

主题插件的 `tools/test-client.mjs` 用**桩 ctx + 桩 DOM** 跑真实 `client.js`。
桌宠沿用同一套路，共 **338 项断言**，无框架依赖（纯 `node:assert`）：

- **状态机**（156）：每种事件 × 每种 `TurnEndReason`、跨会话优先级聚合、

  气泡优先级抢占与静默期、未知事件前向兼容、素材清单路径安全；
- **路由**（61）：三道围栏、SSE 帧格式、端口自发现、hub 生命周期；
- **浏览器半边**（77）：bundle 契约、插槽冲突不中断 `apply()`、
  位置夹取与持久化、**定位约束**（必须 fixed、不能铺满、z-index 不越界）、
  精灵裁剪视口、渲染组件树、**外壳真实 props 形状**（§7b）；
- **端到端**（37）：真实 `apply()` + 真实 `pet.json` + 真读 SSE 帧，
  验证「宿主事件 → 状态机 → 推送」整条链路。

> **单测确实抓到了真实缺陷**，不是走过场：未知状态名泄漏到快照、
> `waking` 永不退出、`native/status` 误算作用户活动、精灵条带没有裁剪视口、
> `onImgLoad` 的 TDZ 错误、空 hello 帧污染快照。**先写测试是值得的。**

#### ⚠️ 教训：断言必须打在**运行路径**上（两种形态都踩过）

1. **测了副本**：`DiagTargetFor` / `DiagActivateHasZOrderFallback` /
   `DiagFindAllowsMinimized` 曾各自是 `PlaceNearPet` / `ActivateWindow` /
   `FindDshWindow` 的**手抄副本**，回退验证时**静默通过**。改法：抽成共享纯函数，
   自检断言打在真函数上。
2. **测了不存在的调用约定**（更隐蔽，真机炸过）：测试一律 `Pet({ runtime })`，
   而外壳渲染 slot 条目时传的是
   `{ ...kit, ...entry.inject, ...slotInjected.props, ...ownerProps }` —— **没有 `runtime`**。
   测试与实现共享了同一个错误假设，于是 **290 项全绿而真机上整片崩溃**：
   条目一渲染就抛 `TypeError`，被外壳 `SlotErrorBoundary` 接住并
   `reportEntryError(abdicate:true)` **逐出单元格**（live slot 树里该条目
   `active: false`，同插槽其余 12 个全 `true`）。症状是桌宠不出现 + 设置页空白，
   **且不报错**（只在浏览器 console）。

   > 改法：`client.js` 用模块级 `pluginRuntime`（`apply()` 装配，`requireRuntime()` 取），
   > 组件**完全不读 `props.runtime`**；测试新增 §7b 按外壳形状断言
   > （`Pet({})`、`Section({ close })`、传 Proxy 陷阱证明不读 props.runtime）。
   > 回退验证：改回 `const { runtime } = props` → **29 项红**。

## 十、反面清单（别做这些）

- ❌ **别让宿主或主进程开原生窗口** —— 主进程 IPC 是封闭白名单，渲染层
  `setWindowOpenHandler` 一律 deny（已核实，asar 内 7 处）。
  **但可以自己 spawn 一个进程**（用官方 `ctx.subprocess`）—— 这是关键区别。
- ❌ **别用 `node:child_process` 绕过 `ctx.subprocess`** —— 会丢掉三样东西：
  服务 dispose 时的自动终止（→ 留孤儿）、沙箱感知、结构化的退出事实。
- ❌ **别用 `position:absolute` 定位窗口内桌宠** —— overlay 被 grid 挤到第二行，会偏一屏。
- ❌ **别给 overlay 层塞满屏容器** —— 子元素自动 `pointer-events:auto`，会挡住整个界面。
- ❌ **别把精灵条带直接放进容器** —— 浏览器会把 33 帧铺开成一条巨长横条。
  必须有「单帧宽的 `overflow:hidden` 视口 + 绝对定位条带」。
- ❌ **别假设单帧是方的** —— 实测 239~288px 宽。拿 `frameHeight` 当宽度会压扁图。
- ❌ **别逐帧各裁各的 bbox** —— 每帧偏移不同，人物会在帧间抖动。要用并集 bbox。
- ❌ **别读会话消息正文** —— 桌宠是表现层，读正文既有隐私问题又会因 DOM 变化而碎。
  只消费事件元数据与 `turn/end` 的 `reason.kind`。
- ❌ **别在 Client 侧用 `retain()`**（本方案不需要）—— 万一用了，**别忘 `release()`**。
- ❌ **别把素材路径拼进 URL** —— 必须走白名单校验（目录遍历）。
- ❌ **别假设所有平台都有 `data-windows-titlebar`** —— 那是 Windows 专属标记。
- ⚠️ **PowerShell 版本与 `.ps1` 编码**（实测澄清，别照抄旧结论）：
  - 本机 `pwsh` 是 **PowerShell 7.6.6（Core）**，`$PSHOME` = `C:\Program Files\PowerShell\7`；
    Windows PowerShell 5.1 在 `$env:SystemRoot\System32\WindowsPowerShell\v1.0\powershell.exe`。
  - **不要写 `& "$PSHOME\powershell.exe"`** —— 会话在 PS7 下时该路径不存在，
    命令会静默失败（实测踩过：以为部署成功，其实什么都没跑）。
    直接 `& .\tools\deploy.ps1`（用当前 shell）即可，脚本本身与版本无关。
  - **5.1 需要 BOM、PS7 不需要**：5.1 把无 BOM 的 UTF-8 `.ps1` 当 ANSI/GBK 解码，
    中文会乱码；PS7 按 UTF-8 读，且 `Out-File -Encoding utf8` **不写** BOM
    （5.1 会写 —— 这正是当初写坏 `profile\package.json` 的原因）。
  - 结论：**统一用 PS7**。它既能跑 5.1 时代的脚本（`deploy.ps1` 一字未改跑通），
    又不会因 BOM 被 `edit`/`write` 工具剥掉而失效。
    反向不成立：**5.1 跑不了 PS7 语法**（`&&`、`||`、`??`、三元 `? :`）。
- ❌ **别指望 disable→enable 能重载 Host 半边** —— 宿主缓存 ESM 模块，
  重载只重跑 `apply()`，不会重新 `import` `src/*.js`。用 `/pet/diag` 的 `build` 字段确认。
- ❌ **别给窗口内 overlay 加新功能**（v2 决定，见 README 的说明）。
  它已冻结为**兼容兜底**：只修 bug，不再补滚轮缩放/右键菜单/画廊/托盘。
  理由是实测出来的 —— **12 次提交**是"两半边必须同步"的税，
  而 overlay 还要额外养 464 行 CSS、自判主题、自存位置，外加一堆 DSH 内部知识
  （`position:fixed` 绕 grid、`pointer-events:auto` 陷阱、`z-index` 上限）。
  最严重的一次真机事故（客户端整片崩溃、设置页空白且不报错）**只可能发生在 overlay 上**。
  决定性事实：**DSH 的 webServer 只绑 loopback**，网页版用户 DSH 也在本地跑，
  exe 永远连得上 —— overlay 的价值只剩非 Windows 与 exe 被杀软拦两种边缘情况。
- ❌ **别把 `sessionController.prompt()` 的 `mode` 当成可选**（真机炸过：发送必 502）。
  上游 zod schema 是 `z.union([z.literal("queue"), z.literal("steer")]).readonly()`，
  **没有 `.optional()`**。排队用 `'queue'`。
- ❌ **也别漏 `prompt()` 的第二个参数 `signal`**（同一个 502 的**第二个**成因，更隐蔽）。
  描述符是 `cancellation: { parameter: 'signal' }`，网关取**第 2 个实参**并直接
  `signal.throwIfAborted()`；少传 →
  `TypeError: Cannot read properties of undefined (reading 'throwIfAborted')`。
  必须是**真 `AbortSignal`**。
  教训：**"症状一样"不等于"原因一样"** —— 我只修了 `mode` 就以为好了，
  因为两种漏传在界面上**都是 502**，而当时**看不见真正的 message**。
- ❌ **兜底错误文案不许吃掉原始原因**。exe 原先 502 只显示"发送失败（HTTP 502）"，
  把响应体的 `message` 丢了 —— 上面那个 bug 因此拖了两轮。诊断路径的铁律：
  **把宿主/上游给的原文带上，并写进日志**（`PetInput.DescribeSendError` + `pet.log`）。
- ❌ **别在 `props` 里找插件自己的运行时**（真机炸过：客户端整片崩溃）。
  外壳渲染 slot 条目的 props 只有
  `{ ...kit, ...entry.inject, ...slotInjected.props, ...ownerProps }` ——
  `runtime` 不在其中。用模块级单例（`client.js` 的 `requireRuntime()`）。
- ❌ **别让"总开关/显示模式"只在启动时生效**。`enabled` 与 `mode` 改完必须
  真的启停 exe（`syncNativeProcess()`），否则"关掉了桌面那只还在"。
  判据只能有一份（`nativeWanted()`），启动与设置变化共用。
- ❌ **别发空的 SSE hello 帧**（`data: {}`）—— 会让客户端的 `petState`/`rev` 变成
  `undefined`（违反契约 §2 必填字段），并破坏 `rev` 单调性（实测抓到过）。

### v3 新增的反面清单（番茄钟 / 语音 / 互动 / 聊天那一轮）

- ❌ **别在运行时合成语音** —— 实测 GPT-SoVITS 冷启动 30.6 秒、热态 5 秒/句，
  而桌宠要在一秒内回应点击。台词必须是**封闭集合**，构建期压成 mp3。
- ❌ **别用 `$input` 当 PowerShell 形参名** —— 那是自动变量（管道输入枚举器），
  同名形参静默失效：`-i $input` 展开成空，ffmpeg 报
  "Error opening input file -ac"（把下个开关当成输入路径）。
  实测：合成 6 条全成功、转码 0 条成功。
- ❌ **别用 `Measure-Object -Property x` 读 `[ordered]@{}` 的键** ——
  字典的键不是属性，会抛 "The property cannot be found"
  （实测：19 个 mp3 全生成成功，却卡在最后一步汇总）。
- ❌ **别把数值字段直接查表**（`TABLE[kind] ?? null`）——
  `TABLE['__proto__']` 返回 `Object.prototype`、`['toString']` 返回函数，
  "未知动作"会被当成合法配置一路传下去（实测 `interact('__proto__')`
  返回了 `accepted: true`）。必须 `hasOwnProperty`。
- ❌ **别只靠下游返回 null 当白名单** —— 路由层的白名单要在**串进入内部之前**
  生效。回退验证抓到过两处：删掉路由层白名单后测试**全绿**（`__proto__` 已进内部）；
  语音路由不检查 HTTP 方法（`POST /pet/voice/<name>` 也能读到文件）。
  "看起来有防线、实际靠巧合"比没有防线更糟。
- ❌ **别以为 `path.join(root, p)` 会挡住绝对路径** ——
  `path.join(root, 'C:\\Windows\\win.ini')` 在 Windows 上返回的就是那个绝对路径本身，
  `startsWith(root)` 于是形同虚设。**先显式拒绝对路径与盘符**。
- ❌ **别把绝对路径/盘符判断、`IsNaN` 判断这类"看起来冗余"的行随手删掉** ——
  先回退验证。`double.IsNaN` 那行我一度断言是冗余的（"NaN 参与比较都是 false"），
  探针证明：删掉它、同时把比较写成 `!(dist > 4)`（看起来自然的等价变形），
  NaN 就会**通过** —— 自检立刻失败 2 条。
- ❌ **别让"档位/等级"类数值升不上去** —— 递减序列以 0 结尾时，
  每个动作一天只能贡献十几分，而第二档门槛 20，用户**永远到不了第二档**，
  整个系统就是个装饰。递减管"单次不能无限赚"，日上限管"总量不能无限赚"，
  两道闸各管一件事；并写一条**设计不变式**断言"单日潜在收益必须能跨过第二档"。
- ❌ **别在 exe 侧自算"该提醒了"** —— 番茄钟阶段结束的判定与提醒都在 Host
  （唯一真相）。exe 只用 `endsAt` 做显示用的本地插值；暂停时必须回落
  `remainingMs`（`endsAt` 为 null，拿去算会得到荒唐的负数）。
- ❌ **别用时间戳做"一次性事件"的去重** —— 同一毫秒两次互动时间戳相同，
  会漏掉第二次。用**递增序号**。
- ❌ **别覆盖用户手写的 `AGENTS.md`** —— 判据是"插件标记必须在**第一行**"；
  放宽成"文件里含这个字符串"会把引用过标记的用户文件误判成我们的产物。
  这是不可逆的数据丢失，值得一条专门的断言（含反向断言：我们自己的产物
  **要能**被更新，否则功能永远切不动）。
- ❌ **别给"不可用的功能"留入口** —— 聊天不可用（宿主没装配 / 用户关了）时，
  输入窗的下拉里**不显示**"聊天"选项，而不是留着让你点了报错。
  `available` 与 `enabled` 分开报，`reason` 区分"宿主不行"与"用户不要"。
- ❌ **别给"计时器"类功能默认开** —— 装完插件就自己开始 25 分钟倒计时、
  或突然开口说话，都是**骚扰**。番茄钟与语音默认关，用户主动开才生效。
- ❌ **别让"冷却期"挡住"反应"** —— 冷却中不涨分可以，但必须仍有反应
  （气泡/语音/表情）。点了没反应比没涨分更像坏了。
- ❌ **别把 `PetJson.Parse` 当成"坏输入必返回 null"** —— 它是**容错解析器**：
  `"{ not json"` 返回一个空对象而不是 null。所以解析完必须检查**关键键存在
  且类型正确**，否则坏响应对变成"合法但空的菜单"（界面上表现为空子菜单）。
- ❌ **别用 `Get-Content` 后的相对路径喂 .NET 静态方法** ——
  `[System.IO.File]::ReadAllText("tools\x.json")` 按进程 CWD 解析，
  与 PowerShell 的当前目录**不一致**，会写错位置甚至**清空目标文件**
  （实测把 `voice-lines.json` 清零过）。一律先 `Resolve-Path` 成绝对路径。
- ❌ **别在"人设"里复制世界观** —— 用户要的是**加法**：共享背景（`personas/shared/`）
  改一次影响所有风格，风格文件只写"她怎么说话"。复制 N 份的后果是
  "改了一处、另外五处还是旧的"，而且没有任何报错。
- ❌ **别让两条注入路人设不一致** —— 系统提示词 section 与 `AGENTS.md` 兜底
  必须写**同一个组合结果**。否则同一份人设在不同宿主能力下表现不同，
  现象是"有时记得住设定、有时忘了"，极难定位。
- ❌ **别把"记忆"做成无底洞** —— 它会被注入每一次请求的系统提示词，
  不裁剪迟早撑爆上下文（而且每轮都在为它付 token）。
  超上限要裁**最旧**的，并且**保住本次新增**（宁可超一点也不能丢新记忆）。
- ❌ **别信模型的记忆提炼输出** —— 它可能回一句解释、可能回 NONE、
  可能一次吐 10 条。解析必须：认 NONE、丢解释行、限 3 条、单条截断。
  否则记忆文件里会混进"好的，我提炼了以下事实："这种垃圾，而且越滚越大。
- ❌ **别用"长度"猜模型输出是不是事实** —— "用户叫小明"只有 5 个字但是好记忆。
  要按**形状**判：解释性句子几乎都以冒号结尾或以"好的/以下/总结"开头。
- ❌ **别让记忆写入阻塞聊天** —— 提炼是 fire-and-forget，失败只记日志。
  记忆是加分项，不是必需项；为它拖慢一次回复是本末倒置。
- ❌ **别把 `resolveAgent` 当成一定有** —— 它是 `sessionController` 的方法，
  宿主版本/装配不同就可能没有。拿不到就退回 `AGENTS.md`，
  绝不能让"人设/记忆挂不上"变成"聊天不可用"。
- ❌ **别用 `ctx.on('assistant/message')` 订阅会话事件** —— 那是
  `SessionEventMap` 里的事件（经 `session/event` 派发），**cordis 根上没有这个
  事件名**。而 `ctx.on` 对未知事件名**不抛错**，于是订阅静静地永不触发：
  没有报错、没有警告、日志干干净净，功能就是不工作。
  正确做法：在 `session/event` 的监听器里按 `event.type` 分派。
  教训是通用的：**"没有报错"不等于"订阅成功"** —— 新增订阅后必须有一条
  端到端断言证明它真的被触发过（本项目的 599 项断言全绿时，
  这条回复通道是**完全没被测试覆盖**的）。
- ❌ **别给"必须显示正文"的气泡留自动选图的自由** —— 状态机有一条正确性
  规则：图自带文字时**不叠 Host 文案**（防止两段文字打架，契约 §4 的 `hasText`）。
  而全池兜底会挑到「么么哒」「好耶！」这类自带中文的贴纸 ——
  于是正文被整段吞掉，用户只看到一张贴纸，而优先级/时长全都是对的
  （状态机"成功地"弹了一个没有内容的气泡，从指标上完全看不出来）。
  要显示正文就**显式指定无文字的图**；一张都没有就干脆不配图。- ⚠️ **asar 头部是三层 uint32，JSON 从偏移 16 开始**：
  `[0..3]=4`、`[4..7]=头部长度`、`[8..11]=内层长度`、`[12..15]=JSON 长度`、
  `[16..]=JSON`。按 12 起读会得到 4 个垃圾字节 + 完整 JSON ——
  `JSON.parse` 报 "Unexpected non-whitespace character after JSON at position 1"
  （它把开头的 `0` 当成了合法数字，位置 1 处多出东西）。
  **别靠容错回退蒙对**：回退到 `indexOf('{')` 会解析出一个**子树**，
  看着成功、实际少了一半文件（本项目探针正是这么被误导了一轮）。

### v4 新增的反面清单（设置页第三轮重做：页签 / 卡片 / 折叠）

背景：用户为"设置界面很混乱"提了**三次**。前两轮修的都是**能被断言抓到的错**
（14 个控件是死的、CSS 类名没定义、滑杆数值换行、分隔线看不见），
但用户第三次说的还是"混乱" —— 说明**组织方式**才是主因，不是个别 bug。
量出来的实情：一列平铺 2556px、7 组 40 行 42 控件、要滚三屏；
而 DSH 外壳自己的设置页（Models / General）是**卡片 + 一屏**。
修法：六个页签（每页 ≤10 行、实测 837px 内一屏放得下）+ 卡片可折叠 +
字号阶梯 + 单一控件尺度。

- ❌ **别把"没报错的功能性 bug"当成"界面不混乱"** —— 前三轮我把"控件是死的"
  修完了，用户看到的仍然是"一片乱"。**"能不能用"和"看不看得懂"是两个验收面**，
  前者有断言守得住，后者只能靠**量几何 + 对着外壳自己的实现比对**。
- ❌ **别让同一类信息出现在两个位置** —— 说明文字原先有三种写法并存
  （`Toggle` 的说明在控件下方通栏、下拉框的说明挤在标签与控件之间、
  独立的 `note` 段落又满行一段）。后果不是"难看"，而是**每一行都要重新找**
  "这句话在说哪个控件"。现在只有一种位置：行标题下面、左列里面。
  拿不定主意时，去抄**外壳自己的行结构**（`.title` 14px + `.description`
  12px 二级灰，同在左列）。
- ❌ **别把字号阶梯压成 11/12/13** —— 三档只差 1px，等于没有层级：
  屏幕上是一片同权重的灰，用户的原话是"看不出重点"。
  外壳用 16 / 14 / 12（差 2px）才读得出层级。这条现在有断言守着
  （设置页规则里的 `font-size` 只允许 12/14/16）。
- ❌ **别"一行一个概念"到把卡片切成单行卡** —— 「主题」单独成卡多花
  卡片头 40px + 间距 10px（实测 100px），直接把「外观」页顶过一屏。
  卡片是**分组**手段，不是"每个设置一张卡"。
- ❌ **别在 DOM 之外给 React 元素塞属性**（`node.props.tab = x`）——
  开发构建的 props 是 `Object.freeze` 过的，真机上直接抛错，而**测试桩不会**
  （桩返回的是普通对象）。装配期分类要用外部结构（本项目用 `{tab, node}`）。
- ❌ **别用"改个测试缝再重渲染"来模拟切页签** —— 桩的 `useState` 会把首次
  `init()` 缓存住，只归零 hook 游标的话第二次渲染读到的还是旧值，
  于是"切页签"的断言**假绿**。要走真实的 `onSelect`（本项目 `switchTab`）。
  同理：`collectByType` 不展开函数组件，v4 的控件挂在 `Row` 的 `control`
  **prop** 里 —— 只走 `children` 的检查器会一个控件都找不到。
- ❌ **别在给字典"插键"时把锚点那一行替换掉** —— 我用"替换 anchor"的办法插
  17 个新键，锚点恰好是 `advancedHint` 那一行，于是它从两份字典里一起消失；
  而 `t()` 取不到键时**回落成键名本身**，诊断页上就一本正经显示着
  `advancedHint`。已加断言：源码里每个 `t('x')` 的 x 必须在 zh/en 两份字典里。
- ❌ **别指望"页签只是显示层"** —— 切页签会把非当前页的卡片**整个卸载**，
  非受控输入框（记忆框、聊天输入框）会按 `defaultValue` 重建：
  用户打了一半的草稿会被"已保存的那一份"覆盖。`defaultValue` 必须优先取
  挂在 `Section` 上的草稿 ref（活得比卡片久），并且单独立一条断言。
- ⚠️ **`client.js` 是 CRLF，`styleText()` 返回的是模板字符串**：
  多行 `edit` 锚点必须先 LF 归一化（否则静默不生效），CSS 注释里
  **绝不能出现反引号**（会提前结束模板字符串）。这条踩过三次，
  现在两件事都由脚本断言守住（见 `.scratch/splice-settings.mjs`）。

### v4.1：桌面端 ↔ 设置页 的同步（用户报"滚轮调完大小，设置页不跟着变"）

- ❌ **别让"设置"只有一个写入方向** —— 这是本轮的主因。
  `state.settings` 原先只有两个写入点：挂载时 `GET /settings` 一次、
  以及设置页自己 `updateSettings()`。而宿主**每一帧快照都带着 `settings`**
  （`exeSettings()` 那 13 个字段），客户端拿到了却**从来不读**。
  于是任何"不是设置页发起"的改动都到不了界面：
  桌面端滚轮缩放、桌面端托盘菜单、另一个窗口里改的设置、宿主对值的夹取。
  症状是"我在桌面端调完，设置页还显示旧值"，**而且没有任何报错**。
  教训是通用的：**有上行通道不代表有下行通道** —— 加一个"能改"的入口时，
  同时问一句"别人改了，我怎么知道"。
- ❌ **别把快照里的设置无脑 emit 出去** —— 快照每帧都来（状态一变就广播），
  无脑 emit 会让设置页每帧重渲染一次，而且重渲染的内容"看起来没变"，
  排查起来极费劲。逐字段浅比较足够（设置是平的），与宿主侧
  `#emitIfChanged()` 同一套判据。
- ❌ **别让 exe 本地改完设置却不回报** —— 托盘里的「缩放 / 点击穿透 /
  总在最前 / 显示气泡」原先**只改本地**。设置页读的是宿主那份，
  本地改完不回报，两边永远分叉，同样毫无报错。
  新增了一个"能改设置"的入口时，回报那一行必须一起写
  （现在有 `ReportSettingFlags` 收口，托盘与右键菜单走同一条）。
  另外：开关**不需要去抖**（一次点击就是一个终值），缩放才需要（滚轮是连续事件）。
- ❌ **别"先清定时器、再判断要不要清"** —— `scheduleTick()` 原先的判序
  会把定时器清掉却不补上：`tickFloor` 还留着旧值 ⇒ 后续每次算出同一个 delay
  都再次早退 ⇒ **定时器永远回不来**。后果不是"晚一点"而是"没有了"：
  `sleeping` 与气泡过期只靠这个 15 秒兜底，丢了它桌宠**再也不睡觉、
  气泡再也不消失**，且毫无报错。
  为什么现在才暴露：这条路径要"连着两次算出同一个 delay"才走到，
  而 `onApplied`（每个事件后重排）落地之前它根本走不到 ——
  **一个原本不可达的缺陷会因为"调用变频繁"而变成必现**。
  判据：**先判条件，再动副作用**。
- ⚠️ **看得见才好测**：这类"定时器丢了"的 bug 从外部完全观测不到，
  所以给 `/pet/diag` 加了 `tick: { armed, floor }` —— e2e 据此立了回归断言
  （连着两个"无 deadline"的事件之后 `armed` 必须仍为 true，回滚验证有效）。
  **加一个可观测点，比写一段解释便宜。**
- ❌ **回滚验证脚本自己也会骗人** —— 我第一版用"LF 归一化 + 下标换算"改文件，
  结果把 `index.js` 改出语法错误，而脚本把"跑不起来"当成"没有失败项"，
  报了一句"仍然全绿"。现在：① 直接用字符串替换（先断言唯一），
  ② 把"跑不起来"单列一种结果，绝不与"变红"混为一谈。

### v5 新增的反面清单（互动手势 / 番茄钟统计 / 「今天」页签）

背景：用户提了两件事 ——「当前的番茄钟太简单了」与「互动当前方式，通过右键
就点个按钮，很奇怪，能不能加一些更有意思的」。前者的实情是"跑完什么都不留下"；
后者的实情是**三个动作在机制上完全相同**（固定加分、固定台词、固定表情），
结果不随"什么时候、她当时在干什么"变化 —— 所以它确实就是三个按钮。

- ❌ **别把"没有专属池"当成"用默认池"** —— 这是本轮最隐蔽的一个**现存缺陷**。
  `interact/<kind>` 这些 key 原先没有专属表情池 → `pickEmoteFile` 返回 null →
  回落**全池随机**。而全池 42 张里 **36 张（86%）自带文字**。状态机有一条
  正确性规则：**图自带文字时不叠 Host 文案**（契约 §4 的 `hasText`）。于是：

      用户点她一下 → 她该说「嗯…这样也挺好的。」
      实际显示    → 一张写着「略略略」的贴纸，那句话**一个字都没出现**

  而优先级、时长、`hasText` **全都是对的** —— 指标上完全看不出来，也不报错。
  反面清单里其实早就记过这条（"别给必须显示正文的气泡留自动选图的自由"），
  但当时只修了「全池兜底」那条路径，**互动这条漏了**。
  教训：**"有兜底"不等于"兜底是对的"** —— 兜底会掩盖"忘了配"。
  现在有断言：每个互动情境的池必须**非空**且**全不带文字**。

- ❌ **别在"生成产物"的遍历顺序表里漏掉新 key** —— `prepare-pet.py` 的
  `BUBBLE_KEY_ORDER` 是**台账文档**的遍历顺序。新的 `interact/*` 不在里面，
  于是产物 `emotes.data.js` 有、**台账文档里查不到**（实测 0 行）。
  而生成 `emotes.data.js` 走的是另一条路径（`by_key`），所以症状**只在文档里** ——
  比"功能坏了"更不容易被发现。台账存在的意义就是消除"只能读代码回答"。

- ❌ **别让一个动作有"两个入口"** —— 手势落地后，右键菜单里的互动项就成了
  同一个动作的第二个入口，用户会以为它们不一样。但**也不能一删了之**：
  `feed`（投喂）/ `praise`（夸奖）是"对她做一件事"、不是"碰她"，
  **没有对应的手势**，删掉入口等于删掉功能。
  判据写成了集合关系断言：**菜单 ∪ 手势 = 全部动作，且两者不相交**。
  它同时防"加了新动作却忘了给入口"（**永远无法触发**，而且 Host 表里有它、
  白名单也认它，只是没人能发出那个请求 —— 零报错）。

- ❌ **别用"缺键"表达"用户设成了 false"** —— 三个手势开关的缺省值**刻意不同向**：
  长按/抛掷默认 `true`（要主动做手势才触发），悬停/呼吸默认 `false`（骚扰型）。
  而旧 Host 的快照里**根本没有这三个键**。直接 `Bool("flingEnabled", false)`
  的话，升级插件后手势会**整个失灵**且没有任何报错。守卫是 `Has*` 标记：
  **没有键 = 不动现状**。

- ❌ **别让"缺省值"有两个真相** —— 回滚验证抓到过我的一个**假断言**：
  我断言"把 `hoverReact` 的缺省值改成 true 会变红"，改坏之后**自检仍然全绿**。
  因为那段解析是 `if (键存在 && 是布尔) { Bool(键, X) }` —— `X` **永远用不到**，
  真正的缺省值活在 `Program` 的字段初始化里，解析里那个常量是**死代码**。
  同一个语义两份、其中一份不可达 —— 假断言就是这么来的。
  现在缺省值收进 `PetSettingsInfo.Default*()`，两边都读它。

- ❌ **别在 e2e 里留下"闩锁"污染下游用例** —— 我新加的用例全绿，却让一条
  **完全无关的老用例**红了。根因：我给一个会话置了 **error 闩锁**，而
  error(60) 的优先级**高于** happy(50) —— 下游那条用例无论怎么派发
  `completed`，聚合状态都还是 error，而失败信息看起来与本节毫无关系。
  e2e 的用例共享一个真实宿主，**"我这条绿了"不等于"整体还绿"** ——
  新用例必须自己收拾干净，而且要有断言证明收拾干净了。

- ⚠️ **回滚验证自己也会骗人（第二次）** —— 我第一版是**直接改产物**
  `emotes.data.js` 来验新断言。三条"全部有效"里有两条其实是**另一条断言**
  （"生成物没过期"）在变红，不是我要验的那条。

### v13 新增的反面清单（高指针增益下的手势容差）

背景：用户说"我鼠标DPI平时开的比较高，所以很多手势触发不了，怎么回事"。
这不是手感问题，是一个**可量化的判据错误** —— 见前两条。

- ❌❌ **别把"人的动作容差"写成绝对像素** —— 这是本 bug 的根。
  手势容差是**屏幕物理像素**（点击 4px / 摸头 6px），而它要吸收的量是
  "按住鼠标时手抖了多少**像素**"：

  ```
  手抖像素 = 手抖的物理距离 × 鼠标硬件 DPI × 指针增益
  ```

  于是**鼠标越灵敏，手势越难触发** —— 完全反直觉。实测本机
  `SPI_GETMOUSESPEED = 12`（增益 **1.5×**），4px 容差实际只剩 2.7px；
  1600 DPI 鼠标 0.3mm 的手抖就是 18.9 counts → **28.3px**，远超 6px 的摸头容差。
  修法：容差 = 基准 × 增益（`GestureTolerance.FromGain`），**下限是基准**
  （低增益不许更难触发），上限 24/36px（否则真拖动会被判成点击）。

- ❌❌ **别指望自动检测能修完 —— 有些因子根本读不到** ——
  指针增益能读（`SPI_GETMOUSESPEED`），但**鼠标硬件 DPI 没有任何 API**，
  而用户说的"我 DPI 开得高"恰好就在那一半。所以必须**同时**给一个用户
  能自己拧的旋钮（`gestureSensitivity`，1.0~3.0，默认 1.0 = 不变手感）。
  只做自动检测 = 把"完全没救"换成"救一半"，而用户仍然会来报同样的 bug。

- ❌❌ **别让"一次越界"变成"这次按住永久作废"** —— bug 的另一半。
  `_movedSincePress` 一旦置位就永久为真，`OnHoldTick` 靠它**停掉**长按计时器
  → 手抖一下，摸头在这次按下里就彻底没了（哪怕手立刻回到原位）。
  高增益下容差只有 4px，"抖一下"是常态 → 摸头大面积失灵。
  改成**可恢复**的 `_holdStill`：越界时把静止计时**清零**（`_pressClockMs = nowMs`），
  稳回来重新静满 `PatMinMs` 照常报级。
  ⚠️ 两个容易写错的细节：① 手**一直在容差内**时**不许**重置计时，
  否则 500Hz 鼠标下永远攒不满 350ms，摸头从"偶尔不灵"变成"完全不可能触发"；
  ② `_patLevelReported` **不许**跟着重置，否则来回抖就能反复刷级，
  "一次按住最多 3 级"的上限会被绕过。

- ❌❌ **别只记"成功的手势"** —— 这是本次诊断最大的障碍。
  原先只有成功路径留日志（`单击桌宠` / `长按摸头` / `抛掷 v=`），
  失败那次只有 `EndDrag` 的一句"拖动结束 → x,y"，**没有任何 dx/dy/时长**。
  于是"用户按了 54 次、只认了 4 次点击、2 次摸头"这件事在日志里**完全看不出来**：
  54 条"拖动结束"看起来就像 54 次正常的挪位置。
  现在**每次松手**都记 `dx/dy/ms/v → 判定 [容差]`。
  判据：**失败的路径也要留数据**，否则阈值永远只能靠猜。

- ❌ **别让自检"抄一份"被测逻辑（第二次，v12 之后又犯）** ——
  我第一版让 `DiagHoldTick` 自己抄了一遍长按判定，于是断言测**拷贝**、
  产品走**原件**。回滚验证把 `OnHoldTick` 改回 `_movedSincePress`（= 要修的
  bug），自检**依然全绿** —— 因为断言只驱动了那份拷贝。
  这与 v12 的 `ResolveRelease` 是同一个教训：**两份判据会互相掩护**。
  修法：抽出 `HoldTickCore`，真实计时器与自检都调它。
  ⚠️ 回滚验证本身也会骗人：我第一版写的 R7（拷贝一份**行为等价**的实现）
  必然 GREEN —— 那不是"断言有洞"，而是**那条回滚根本无效**。
  有效的回滚必须让拷贝带上**旧语义**。

- ⚠️ **"接线"必须端到端断言，不能只断言"设置里有这个键"** ——
  v10 那四个开关（`longPress`/`flingEnabled`/`hoverReact`/`pomodoroBreath`）
  在 `settings.js` 里有、设置页能改、`settings.json` 里也存着，但
  `exeSettings()` **根本没发给 exe** → 四个开关全是装饰品，而用户看到的
  只是"手势没法正常触发"。所以本轮加了 `test-pet-native-e2e.mjs` 的
  3b 组：设置写 2 → 断言**快照里是 2** → 断言 **exe 日志里出现
  `sens=2` 且 `click>=8px pat>=12px`**。回滚验证：把 `index.js` 那一行删掉，
  这两条**立刻变红**。

- ⚠️ **回滚验证的匹配串/取值会自己骗人（第四次）** —— 这次是**取值**：
  exe 启动时会先用默认灵敏度打一行 `sens=1`，快照到达后才打 `sens=2`。
  我用 `text.match(...)` 只取**第一处**匹配 → 永远看到启动那行 →
  **接线是好的却报红**。判据：日志断言要取**最后/指定**的那一条，
  不能想当然认为"第一次出现的就是结果"。

### v13.1 新增的反面清单（摸头节奏 + 过渡动画）

用户原话：**"摸头的逐级反应太快了"** + **"你自己选择合适的值，记得加上过渡动画"**。

- ❌ **别把"分级"做成三次独立的瞬时动画** —— 这是本轮真正的缺陷。
  摸头 1/2/3 级原先各自调 `PlayReact("pat", level)`，而 `PlayReact` 是
  "戳一下 → 弹回 1.0"的**瞬时**动画：**每升一级都先 `ResetReact()` 弹回原尺寸**。
  于是三级看起来是**三次一模一样的戳**，用户既看不出"越摸越深"，
  也来不及看清每一级 —— 他说的"太快"其实是这个。
  修法：`PlayPatHold` —— **从当前值起算**（`From = 当前 scale`，不是 1.0）、
  **只加深不回浅**、`FillBehavior.HoldEnd`（按住就停在深度上）、松手才 `EndPatHold` 弹回。
  ⭐ 判据：**"过渡"不是给每一级配个动画，而是让级与级之间连起来**。
  从 1.0 起算就必然弹回去，那就还是三个独立的戳。

- ⚠️ **改节奏常量时必须检查"窗口容得下最后一级"** ——
  `PatMaxMs`(4000) 必须 ≥ `PatMinMs + (PatMaxLevels-1) × PatStepMs`。
  步长 600 → 1200 后是 2750，余量只剩 1.25 秒；再调大就会让**第 3 级永远到不了**，
  而且**不会有任何报错**，只是"三级反应从来没见过"。
  已加断言 (5b) 专门守它。

- ⚠️ **检查间隔要跟着步长走，不能写死"一半"** ——
  原先 `Interval = PatStepMs / 2`。步长 600 时是 300ms，够用；
  步长拉到 1200 后变成 600ms，于是每级最多**晚 600ms** 才报 ——
  手感上就是"我按住不动，她过一会儿才反应"。改成 1/8（下限 120ms）。
  ⚠️ 顺手把它抽成 `HoldTickIntervalMs()`：写在 `StartHoldTimer` 里的话，
  自检只能抄一份常量去断言，改坏了照样绿。

- ❌ **断言初始化值会把自己骗成"永远绿"（本轮第一次踩）** ——
  我写"按住期间最浅的一帧"时把 `shallowest` 初始化成 `1.0`，
  再 `if (s > shallowest)` —— 而 scale 恒 ≤ 1.0，这个分支**永远不成立**。
  结果它恒等于 1.0，看起来像"每级都弹回了"，实际是断言自己坏了。
  判据：**记录"极值"的断言，初值必须取真实起点**（这里取动画前的当前值）。
  这与 v13 的 `match()` 取第一处是同一类错误：**断言的取值方式会伪装成产品缺陷**。

- ❌ **"复位清状态"的断言被上一条断言的残留掩护（回滚 R5 抓到）** ——
  我直接 `ResetReact()` 就查 `!DiagPatHolding`，而前一条末尾的 `EndPatHold()`
  早就把标志清掉了 → 这条**永远为真**，回滚照样全绿。
  判据：**要先真的进入那个状态，再验证它被清掉**（先 `PlayPatHold` 再 `ResetReact`）。

- ❌ **只测"一路加深"就验证不了"不回浅"（回滚 R4 抓到）** ——
  我的用例只走 1→3（单调加深），于是"抖动给出浅目标时不许弹回"的保护
  **从来没被触发**。补一条 3→1 的用例才让它变红。
  判据：**保护性分支必须有一个"本该被拦住"的用例**，否则等于没测。

- ❌ **搬走实现后忘了"旧入口"会变成平行拷贝（回滚 R7 抓到）** ——

### v13.2 新增的反面清单（换素材的过渡）

用户原话：**"切换的时候就一下子消失，又出现一个新的，能不能有点过渡"**。

- ❌ **"过渡"不是"先淡出再淡入"** —— 那是**用户抱怨的那个现象本身**
  （中间有一段什么都没有：先消失、再出现）。正确做法是**交叉淡出**：
  加一层残影 Image，换素材时把旧图放上去淡出，**新图同时在下面立刻可见**。
  全程至少有一张图在屏上 —— 这才是"过渡"。
  判据：**断言里必须同时验"新图立刻可见"+"旧图正在淡出"**。
  只验前者的话，硬切**照样全绿**（硬切时新图当然也是立刻可见的）。

- ⚠️ **残影的裁剪不能照抄 `_image.Clip`** —— `Clip` 是**元素局部坐标**里的几何，
  而残影铺满的是换素材**之后**的窗口尺寸。实测 `working-writing.png` 是
  **266×256**、其余是 256×256 —— 尺寸一变，照抄的矩形就对不上，
  圆角会切在错的位置。修法：只记"旧图要不要圆角"这个**布尔**，
  再用残影自己的 `ActualWidth/Height` 算矩形（与 `UpdatePlatedClip` 同一套）。

- ⚠️ **残影必须 `IsHitTestVisible = false`** —— 它是纯视觉层。
  留着可命中的话，淡出的那 180ms 里鼠标会被一张**正在消失的图**挡住，
  表现为"点一下没反应"（而用户看到的是她在那儿）。

- ❌ **只验"最终状态"的断言，验不出"过期回调"（回滚验证 R5 全绿）** ——
  我给残影加了 `Completed` 回调清图，又加了"代次"防止**过期的回调**
  把新一代残影掐断。然后我写了一条"连续换素材最终清干净"的断言 ——
  而**有没有代次保护，最终都是清干净的**，判据不区分 → R5 必然 GREEN。
  真正要防的是"残影淡到一半突然消失"，那是**清了几次**的差别。
  修法：加**清除计数**，断言"一次抖动只清 1 次"（实测无保护时是 **4 次**）。
  判据：**"最终结果正确"不等于"过程正确"**；防竞态的断言必须盯过程量。

- ❌ **断言卡时间点采样 = 偶发变红（本轮踩到，且是先记后修）** ——
  v13.1 我验"松手平滑弹回"时用 `Pump(PatReleaseMs/2)` 取动画中点，
  而 `Pump` 是**墙钟**计时：调度器一忙，150ms 的泵可能实际跑 400ms，
  动画早已结束并归位 1.0 → **偶发变红**（实测出现一次 300/1，重跑两次全绿）。
  ⚠️ **一个会随机变红的断言比没有断言更糟：它会训练人忽略红色**。
  修法：改判**确定性**的量 —— `_reactScale.HasAnimatedProperties`
  （动画挂上即为 true，不用卡时间点）+ "松手瞬间仍在深处"。

### v13.3 新增的反面清单（右键菜单的现代外观）

用户原话：**"不能用个现代一点的UI吗"**（附右键菜单截图）。

- ❌ **"设属性"改不动 WPF 默认模板，必须换 `Template`** ——
  菜单原来只调了 `Background`/`Foreground`/`BorderBrush`，而 Aero2 模板内部用
  主题级 `StaticResource` 硬绑了自己的画刷 → 那些属性**根本不参与渲染**。
  老观感（系统灰、直角、**左侧一条空图标栏**、通栏硬分隔线、`更多(_M)` 括号
  助记符）全部来自默认模板。修法：`XamlReader.Parse` 拼最小模板（`PetInput`
  的下拉框早就验证过这条路）。
  ⚠️ 菜单模板里 `IsItemsHost='True'` 的 `StackPanel` **必须留着** ——
  少了它菜单会变成空壳，而且**不报错**。

- ❌ **"断言渲染出了内容"是假断言 —— 默认模板也渲染得出内容（回滚 R1 抓到）** ——
  我第一版验"菜单渲染出了内容"（亮度 > 0），而把整段皮肤删掉它**照样全绿**。
  要证明"外观真的变了"，只能**两个都渲染、逐像素比**（`CountDifferentPixels`）。
  实测：换皮肤 vs 默认模板差 **5344** 个像素。判据：**比较类断言必须差分**，
  "非空/非零/渲染成功"这类只能证明"没坏"，证明不了"变了"。

- ❌ **`Template != null` 是恒真的假断言（回滚 R5 抓到）** ——
  我写 `a.Template != new MenuItem().Template`，而 `new MenuItem()` 还没套 Style，
  它的 `Template` 是 **null** → 断言退化成 `a.Template != null` → **默认模板也是非 null**。
  正确做法：另建一个**不套皮肤**的菜单当基准，两者必须不同。

- ❌ **拿"带箭头的项"验"有没有文字"，箭头会替文字背锅（回滚 R5 第二次全绿）** ——
  我数"暗像素"来验文字画出来了，被测项选的是「更多」——**它是子菜单头，有箭头**。
  把 `ContentSource` 改坏（文字全没了）后箭头仍贡献 **31** 个暗像素，
  而阈值是 20 → 照样通过。改成**叶子项**（无箭头/勾选）后实测 **382**，
  改坏时是 **0**。判据：**判据必须只由被测的那件事贡献**。

- ⚠️ **`MeasureBrightness` 不能拿来量"有没有文字"** ——
  它刻意只取**上 1/3 行**（避开文字、只量底色），而菜单项未悬停时底色是
  `Transparent` → 那条带里没有不透明像素 → 返回 **-1**。我第一版拿它当判据，
  **产品是对的却报红**。一个"为量底色而设计"的工具，不能换个用途就用。

- ⚠️ **`HasDropShadow` 牵动的是弹层透明能力，不是"画不画阴影"** ——
  动了它，圆角会被方形弹层切成四个黑角，而**离屏渲染测不出来**
  （`RenderTargetBitmap` 渲染的是元素本身，不经过真实弹层窗口）。
  改不动又验不了的东西就别碰 —— 系统阴影只存在于默认模板里，模板换掉即消失。

- ❌ **构建失败 + 跑旧 exe = 假绿（本轮踩到）** ——
  我插截图代码时把 `PetPomodoro pomo = null;` 挤进了注释行，`csc` 报
  `error CS0103` **构建失败**，但脚本没检查退出码，接着跑了**上一次的 exe**
  → 打印"305 通过"。差一点就当成"改好了"。
  判据：**每次跑测试前必须确认构建真的成功**（查 `error CS` 计数与退出码），
  否则你测的是上一版二进制。

- ⚠️ **装配逻辑必须有自检能走的入口（第三次）** ——
  自检第一版直接调 `PetMenuSkin.Apply`，于是**把产品里那一行删掉自检照样全绿**
  （回滚 R7）。抽出 `PetApp.SkinMenu` 让两边走同一条路径。
  这与 v12 `ResolveRelease`、v13 `DispatchRelease`、v13.1 `HoldTickCore` 是同一个教训。

### v13.4 新增的反面清单（子菜单打不开 —— 我 v13.3 引入的回归）

用户原话：**"桌宠右键的更多没有下一级菜单了"**。

- ❌❌ **换 `MenuItem` 模板必须保留 `PART_Popup`（否则子菜单静默失效）** ——
  `MenuItem` 是 `HeaderedItemsControl`，子项就渲染在模板里那个名为
  **`PART_Popup`** 的 `Popup` 中，WPF 按**名字**找它。v13.3 我换模板时漏了它 →
  子项**无处可显示** → 用户看到"箭头在、点开什么都没有"。
  ⚠️ 最坑的是它**不报错、不抛异常**，而**箭头照样显示**
  （箭头是 `Role='SubmenuHeader'` 触发器画的，与 `PART_Popup` 无关）
  → 视觉上完全像"应该有下级菜单"。模板里还必须给 `IsItemsHost='True'` 的
  面板当子项宿主、`IsOpen` 绑 `IsSubmenuOpen`。
  **同一个契约 `PetInput` 的 `ComboBox` 也有（`PART_Popup`），那次只验了配色。**

- ❌ **"能渲染" ≠ "能交互"：我 7 条回滚全红，却漏了这个（最该记住的一条）** ——
  v13.3 我给菜单写了 7 条断言（模板不同、有文字、圆角、深浅色、子菜单也换模板…）
  **全部通过、7 条回滚全部变红**，但用户一右键就发现子菜单没了。
  因为那些断言**没有一条真的去开一次子菜单**：
  ⑦ 只验"子项也换了模板"——而**子项确实换了模板**，只是没地方显示。
  判据：**换带弹出层的控件模板（`MenuItem`/`ComboBox`/`ToolTip`）时，
  必须有一条断言真的把它打开**。"结构对"+"能渲染"都不蕴含"能交互"。

- ⚠️ **`MenuItem.IsSubmenuOpen` 在项未 `IsLoaded` 时会被压成 false** ——
  我第一版的"打开子菜单"断言把菜单项放进一个**没挂到窗口**的 `ContextMenu`
  就设 `IsSubmenuOpen = true` → `pop.IsOpen` 恒 false →
  **产品是好的却报红**。真因：WPF 对未加载的项只登记"加载后再开"
  （`RegisterToOpenOnLoad`）。验交互必须给**真实宿主**（这里用一个
  屏幕外的 1×1 窗口，不抢焦点、不打扰用户）。

- ⚠️ **判据别只看直接子元素** —— 子菜单弹层的直接子元素是模板里的 **`Border`**
  （圆角壳），`IsItemsHost` 的 `StackPanel` 在它**里面**。我第一版判
  `pop.Child as Panel` → 恒 false → 又一次"产品是对的却报红"。
  改成递归找（`HasItemsHost`）。

### v13.5 新增的反面清单（气泡被裁 + 命名/文案）

用户原话：**"气泡表情有概率显示不全（之前一直也有，但是是偶发情况）"**、
**"切换表情预览，表情预览还有表情包，这几个命名让人很困惑呀"**、
**"表情预览，为什么那几个全都是英文"**。

- ❌❌ **裁剪矩形以"容器左上角"为原点，而被裁的内容是"居中对齐"的（气泡被切）** ——
  `_border.Clip = Rect(0, 0, 图片宽, 图片高)`，而 `_image.HorizontalAlignment = Center`：
  一旦**壳比图宽**，图片被居中（左偏移 `dx>0`），裁剪窗口却停在左边，
  于是**图片右侧被切掉一条**（截图里那道竖直切口）。
  实测（探针 `.scratch/probe-clip2.py`）：壳宽 0.7px → 切 0.7px；
  **人为撑宽 40px → 切 40.7px**。
  ⚠️ 修法必须是"**把裁剪挪到图片的位置**"，不能是"把裁剪扩到整个壳"：
  后者虽然也不切图，但圆角会落到**壳的四角**上，图片自己的四角就变回直角
  （那正是先前修过的"气泡没有圆角"）。回滚 C2 专门钉住这个错修法。

- ❌ **只验"尺寸相等"的断言，发现不了"位置错"（本轮的核心教训）** ——
  既有两条断言验的是"裁剪**尺寸** == 图片**尺寸**"，
  而 bug 下这两者**确实相等** —— 错的是**原点**。
  所以断言必须**同时验偏移**（`DiagClipOrigin` / `DiagImageOffsetInBorder`）。
  判据：**"大小对"不等于"位置对"**。

- ⚠️ **"偶发"往往等于"只在某个中间态才成立"** ——
  壳与图天然等宽（`dx≈0`），所以平时看不出来；只有"上一条气泡更宽
  （如长文字）→ 这一条是图"的收缩过程中，`_border.ActualWidth` 还是旧的大值，
  而裁剪**只在 `SizeChanged` 时重算**，尺寸随后不再变化就把错位裁剪**一直留着**。
  于是表现为"随机某几次显示不全"。判据：复现"偶发"要**制造那个中间态**
  （这里靠 `DiagSpreadBorder(40)`），不能只测稳态。

- ⚠️ **`MeasureBrightness` 之外：只记宽度的日志查不出"右侧被切"** ——
  裁剪日志原来只有 `w=`。加了 `offset=` 与 `壳=` 之后，
  一眼就能看出"图片偏移 40.7 而裁剪原点 0"。**日志要记能区分假设的量**。

- ❌ **"都叫表情"的三个入口，指的是两样东西（命名）** ——
  「表情包…」是**气泡里那张贴图**（bubble 素材）；
  「表情预览」/「切换表情预览」是**她本人的姿势**（sprite 状态）。
  三个都带"表情"，用户无法知道点下去动的是气泡还是她本人。
  改法：**按"动的是谁"命名** —— 气泡侧保留「表情包」，
  她本人侧改叫「姿势」（切换她的姿势 / 换下一个姿势）。

- ❌ **内部状态名直接显示给用户（"为什么那几个全都是英文"）** ——
  子菜单原来把 `idle`/`thinking`/`working` 这些**内部状态名**当标签。
  这些词是给代码看的。改法：显示 Host `STATE_TEXT` 的中文。
  ⚠️ 但这会在 exe 侧产生**第二份**文案 —— 所以必须配一条
  **漂移断言**（`test-pet-interactions.mjs` 把 `StateLabelsZh` 与
  `src/pet/state.js` 的 `STATE_TEXT` 逐条比对）。
  这与 `atlas.js` 的 `VALID_STATES`、`assets/catalog.json` 同策：
  **重复一份就必须有断言钉住**。

- ❌ **只验"数据表对不对"的断言，抓不到"有没有用它"（回滚 N1/N3 全绿）** ——
  我先写了三条验 `StateLabelsZh` 表内容的断言，**全部通过**；
  而把 `mi.Header = StateLabelZh(st)` 改回 `= st`（菜单又变英文）时，
  **表还在、也仍然正确** → 三条照样全绿。
  同理，"三个入口的命名"当时**没有任何断言**，改回旧名也不会红。
  修法：断言落在**接线**上（源码里必须出现 `mi.Header = StateLabelZh(st)`
  与三个新名字面量）。判据：**"料对了"不等于"用上了"**。
